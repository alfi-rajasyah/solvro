# Backend conventions (Express + Prisma + PostgreSQL 15)

Sub-200ms API response is a non-functional requirement — design queries and indexes accordingly.

- **Entrypoint**: `src/index.ts` boots; the app is built in `src/app.ts` (split for testability).
- **No `/api` prefix**: routers mount bare (`/auth`, `/projects`, …). The frontend's `/api` base still works because the vite dev proxy and prod nginx both strip `/api` before forwarding.
- **Env**: `src/env.ts` parses `process.env` via Zod and exits on failure. Import from `./env.js` — never read `process.env` directly.
- **Prisma**: single shared client `src/prisma.ts` — never `new PrismaClient()` in a route (standalone scripts under `scripts/` and `prisma/seed.ts` are the only exception). Code that needs a session that stays put — a Postgres session advisory lock — gets a single-connection client from `createDedicatedClient` in `src/prisma.ts` and must `$disconnect()` it in `finally` (the iTop sync lock, `src/lib/itop/syncLock.ts`). Tables/columns are `@map`ped snake_case; the TS surface is camelCase.
- **Auth**: `src/http/auth.ts`. `router.use(requireAuth)` once at the top of every authed router; authorize actions with `requirePermission("project:write" | "task:write" | …)`; `requireAdmin` gates `/admin`. The JWT carries `{ sub, ver }` only; `requireAuth` loads the account on every request (must exist, be active, and `ver` must equal `User.tokenVersion`) and fills `req.user = { sub, role, permissions }` from the database — a password change or admin reset increments `tokenVersion`, which revokes older tokens (so does `POST /auth/logout`, which revokes every device). `requireAuth` returns early when `req.user` is already set (stacked routers on one mount path), so a request costs one lookup. `requireAnyPermission(...)` is the any-of gate for shared read surfaces. `hasPermission(user, "*")` is the wildcard short-circuit. Authorization is permission-based, never role-name-based — admins can create custom roles with arbitrary permission arrays.
- **Visibility**: `src/lib/visibility.ts`. `projectVisibilityFilter(user, access = "see")`: `project:view-all` (or `*`) sees everything; everyone else matches the project's TAM (`tamId`), OR the project's SA (`saId`), OR ownership of the project's customer (`customer.tamId`), OR membership (`ProjectMember`) — each arm grants the same full access as being the project's own TAM, not just a read (docs/archive/plans/collaboration-and-sharing.md). `customerVisibilityFilter(user, access = "see")`: view-all sees every customer; everyone else sees a customer they own (`tamId`), an unowned customer (`tamId` null), or a customer with at least one visible project (so it inherits the member arm). Both results' only top-level key is `OR` — AND-compose with any sibling `OR`, never object-spread. **Ownership changes are owner-only**: changing a project's TAM, customer or SA, deleting a project, deleting a customer, or managing guest links must not be allowed by membership or by being the SA — use `ensureProjectOwnerAccess`/`ensureCustomerOwnerAccess` (visibility 404 first, then 403 `owner_only`), which re-check with `projectVisibilityFilter(user, "own")` (drops the member and `saId` arms; pass the access level to any new owner-only check). **Changing a customer's owner is stricter** (pentest finding M1, 2026-10-06): `PATCH /customers/:id` allows a `tamId` change only for the current owner, on an unowned customer, or with `project:view-all` — being the TAM of a project under the customer is not enough. The pure twin `canUserSeeProject` must agree with the "see" filter, `saId` arm included. Daily Review scope (`lib/dailyReviewScope.ts`) counts member projects as the caller's own, never SA projects. Id-keyed routes use `ensureProjectVisible`/`ensureTaskVisible`/`ensureCustomerVisible` (404 on purpose, not 403 — don't reveal that a hidden resource exists); a `customerId` taken as a body field (a project or a won-deal handoff) uses `isCustomerVisible` instead and answers 400 `customer_not_found` (pass `"own"` when the field attaches or re-parents a project, as `POST`/`PATCH /projects` and the handoff do). Reuse these — never re-derive scoping ad hoc.
- **Validation**: `validate("body" | "params" | "query", schema)` from `src/http/validate.ts`; Zod schemas at the top of the route file; `z.coerce.*` for query/params.
- **Errors**: throw `new HttpError(status, code, message)` from `src/http/errors.ts`; the global handler renders `{ error, code, details }`.
- **Logging**: shared pino logger from `src/logger.ts`; honor `LOG_LEVEL`.
- **Public (unauthenticated) surface**: two routes only — the guest view in `src/routes/publicShare.ts` and the iTop nudge in `src/routes/webhook.ts` (secret-checked, body-ignoring) — both mounted in `app.ts` before the JSON body parser and outside every authed router (`requireAuth` never runs there). Any new public route must be rate-limited via `src/http/rateLimit.ts`, answer every lookup failure (unknown, expired, revoked, malformed) with the same uniform 404 (the webhook alone adds a 401 for a wrong secret), set `Cache-Control: no-store` and `X-Robots-Tag: noindex`, and `select` only allow-listed columns — never return a whole row or an unfiltered relation.
- **Request logging**: goes through `src/http/requestLogger.ts`, which redacts guest-link tokens (path and `Referer`), `/search` query strings (URL, `Referer`, parsed query) and the `Authorization`, `X-Solvro-Webhook-Secret` and cookie headers. Never log a raw URL, `Referer`, or header object that may carry a secret; new secret-bearing paths must be added to its redaction.
- **Position re-packs take the project lock**: a transaction that re-packs task, section or epic positions, or writes task dependencies, calls `lockProject` (`src/lib/positionRepack.ts`) first, before any row lock — a different order risks deadlocks and duplicate positions.
- **Migrations**: always `prisma migrate dev --name <slug>` — never edit committed SQL.

## Traps

- `prisma migrate dev` is interactive and hangs without a TTY: `docker compose exec -it backend npx prisma migrate dev --name <slug>`. Non-interactive fallback: `prisma migrate diff --script` into a hand-created `prisma/migrations/<timestamp>_<slug>/migration.sql`, then `migrate deploy` + `prisma generate`.
- Plain `docker compose exec backend npm test` inherits the container's dev `DATABASE_URL`. `test/globalSetup.ts` hard-refuses to run against it — it throws before migrating or touching any data unless the database name ends in `_test` — so this fails loudly instead of polluting the dev DB. Isolate:
  `TEST_URL=$(docker compose exec backend printenv DATABASE_URL | tr -d '\r\n' | sed 's|/solvro?|/solvro_test?|') && docker compose exec -e DATABASE_URL="$TEST_URL" backend npm test` (globalSetup auto-migrates `solvro_test`, then truncates every table so each run starts from a clean database — no manual drop/recreate needed).
- **Never point `--shadow-database-url` at the dev database** (trap confirmed 2026-09-24: it wiped every row in `solvro`, including the admin user, and the migration history had to be re-baselined). Prisma resets the shadow database. For the non-interactive `migrate diff` fallback create a throwaway database first (`docker compose exec -T postgres createdb -U solvro solvro_shadow`) and pass that URL, then drop it.
- After `prisma migrate dev` (or `migrate deploy`), the long-running `backend` container's already-loaded Prisma Client is stale until `docker compose restart backend` — a route that reads/writes a column the migration renamed or dropped 500s with "column … does not exist" until the container restarts and reloads the generated client.
- Prisma's generated SQL for removing or reordering an enum's values fails on rows still holding one of the removed values (`ALTER TYPE ... USING` can't cast a dropped label). Hand-write that migration instead: backfill the affected rows into a temporary column first, create the new enum type, cast the column from the temp column, then drop the temp column and the old type.
